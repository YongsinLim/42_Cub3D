cub3D: 3D Raycasting Engine in C

Building a first-person 3D perspective from a 2D tile grid using Digital Differential Analysis (DDA)

🕹️ Inspiration

Inspired by id Software's legendary Wolfenstein 3D (1992) created by John Carmack, running smooth 3D rendering on 286/386 hardware without 3D graphics cards.

📐 Core Technique

Raycasting with DDA: Casting 1 ray per vertical screen column, finding exact grid intersections in constant steps, and projecting textured wall slices.

Part 1: Foundational Concept

How 2D Becomes 3D: Raycasting vs True 3D

Why raycasting was revolutionary: transforming an $O(N^3)$ 3D problem into simple $O(W)$ 2D calculations

🧠 The Core Illusion
  • The game world is strictly 2D: a flat matrix of cells where '1' is a wall and '0' is walkable floor.
  • The player is a 2D point $(x, y)$ with a viewing angle $\theta$.
  • Instead of complex 3D polygon math (matrix transformations, z-buffering, rasterization), we cast one 2D ray per horizontal pixel (e.g., 800 rays for an $800 \times 600$ window).
  • When a ray hits a wall at distance $D$, we draw a vertical line on screen whose height is inversely proportional:
    Line Height = $\frac{\text{Screen Height}}{\text{Perpendicular Distance}}$
  • Walls far away appear small; walls close appear tall. This creates full 3D depth perception!

⚙️ RGB Bitwise Color Packing

In graphics programming, an RGB color $(R, G, B)$ is stored in a single 32-bit integer (0x00RRGGBB):

// parse_rgb() logic
int color = (r << 16) | (g << 8) | b;

// Example: R=220 (0xDC), G=100 (0x64), B=0 (0x00)
r << 16 :  00000000 11011100 00000000 00000000
g << 8  :  00000000 00000000 01100100 00000000
b       :  00000000 00000000 00000000 00000000
---------------------------------------------
Bitwise |: 00000000 11011100 01100100 00000000
Result  : 0x00DC6400 (one single 32-bit int)

Strict Validation: We verify exactly 2 commas, and verify each string contains purely digits using is_valid_num().

Part 4: Map Validation

Map Enclosure: Iterative BFS Flood Fill

Why recursive flood fill is dangerous and how our BFS queue guarantees safety

⚠️ The Recursive Stack Problem

A naive implementation of flood fill uses recursive calls:

void flood_fill(int r, int c) {
    // On large open maps (e.g. 100x100 = 10,000 cells)
    // recursive stack frames consume stack memory
    // -> STACK OVERFLOW / SEGFAULT!
    flood_fill(r+1, c);
    flood_fill(r-1, c);
    ...
}

Our Solution: An iterative Queue (BFS) allocated on the heap:

  • Uses t_queue struct with fixed array of t_point.
  • Enqueue player start $(r, c)$.
  • Dequeue current point, check 4 neighbors (Up, Down, Left, Right).
  • If a neighbor is out of bounds or an open space, the map is NOT enclosed!
🛡️ Inner Spaces vs Outer Spaces

A tricky edge case: In .cub maps, external spaces padding the map are legal, but holes inside walls are strictly illegal!

# Legal external padding (spaces outside):
   111111
 11100001
 100N0001
 11111111

# Illegal hole inside walls (player can leak):
 11111111
 100 0001  <-- Space inside walkable area!
 100N0001
 11111111

Two-Pass Algorithm:

  1. mark_outer_spaces(): BFS starting from external border cells marks all true outside spaces as 'X'.
  2. flood_fill_bfs(): BFS from player. If it touches 'X' $\rightarrow$ unenclosed boundary; if it touches raw ' ' $\rightarrow$ internal hole!
Part 5: Camera Geometry

The Vector Camera Model (FOV & Direction)

How two 2D vectors define the player's view and perspective plane

🧭 Direction & Camera Plane

Instead of calculating slow trigonometric angles for every ray, we represent the player with two 2D vectors:

  • Direction Vector $(\vec{dir})$: Points where player is looking. Normalized $|\vec{dir}| = 1.0$.
  • Camera Plane Vector $(\vec{plane})$: Perpendicular to direction vector. Represents the screen surface!
// Field of View (FOV) is determined by ratio:
FOV = 2 * atan(|plane| / |dir|)
// Setting |dir| = 1.0 and |plane| = 0.66 gives:
FOV = 2 * atan(0.66 / 1.0) = 66°  (Standard 90s FPS FOV!)

Spawn Presets:

  • North: dir = (0, -1), plane = (0.66, 0)
  • South: dir = (0, 1), plane = (-0.66, 0)
  • East: dir = (1, 0), plane = (0, 0.66)
  • West: dir = (-1, 0), plane = (0, -0.66)
Part 6: Raycasting Engine

Digital Differential Analysis (DDA) Explained

Why we don't step by small increments and how DDA checks wall hits in discrete steps

❌ The Slow / Buggy Way: Fixed Step

Stepping forward by small distance $\Delta = 0.05$:

  • Extremely slow (hundreds of loops per ray).
  • If step size is too big, rays can jump through thin walls or corner seams.
  • If step size is too small, FPS tanks on large open rooms.
✅ The Fast Carmack Way: DDA

Instead of arbitrary steps, DDA jumps only to the next vertical or horizontal grid line!

  • A cell in our map is always $1.0 \times 1.0$ unit.
  • At each step, compare distance to next vertical line (X-side) vs next horizontal line (Y-side).
  • Advance by whichever distance is shorter.
  • Guaranteed to never miss a wall cell, in minimal CPU cycles!
💻 The DDA Loop in Code
// raycast_main.c: perform_dda()
while (game->ray.hit == 0)
{
    // Jump to next grid boundary in X or Y
    if (game->ray.side_dist_x < game->ray.side_dist_y)
    {
        game->ray.side_dist_x += game->ray.delta_dist_x;
        game->ray.map_x += game->ray.step_x;
        game->ray.side = 0; // Hit East-West wall
    }
    else
    {
        game->ray.side_dist_y += game->ray.delta_dist_y;
        game->ray.map_y += game->ray.step_y;
        game->ray.side = 1; // Hit North-South wall
    }
    // Check if tile is a wall
    if (game->map[game->ray.map_y][game->ray.map_x] == '1')
        game->ray.hit = 1;
}
Part 7: Raycasting Math

Distance Math & Eliminating the Fisheye Effect

Why using straight Euclidean distance distorts walls into spheres

🐟 The Fisheye Problem

If you calculate distance using the Pythagorean theorem $\sqrt{(x_w - x_p)^2 + (y_w - y_p)^2}$:

  • Rays at the edge of the screen travel farther than rays in the center to hit the same flat wall.
  • Result: A perfectly straight flat wall appears curved like a fishbowl!
📐 Perpendicular Wall Distance

We project the distance onto the camera direction vector:

// If we hit an X-side wall:
perp_wall_dist = side_dist_x - delta_dist_x;

// If we hit a Y-side wall:
perp_wall_dist = side_dist_y - delta_dist_y;

This computes the orthogonal distance from the camera plane to the wall, producing perfectly straight flat walls across the entire screen.

Part 8: 2D Projection

Wall Projection: Calculating Column Slices

Turning perpendicular distance into vertical pixels

📏 Projection Calculations

For each vertical column $x$ on screen ($0 \le x < \text{SCREEN\_WIDTH}$):

// 1. Calculate slice height
line_height = (int)(SCREEN_HEIGHT / perp_wall_dist);

// 2. Calculate top and bottom drawing coordinates
draw_start = -line_height / 2 + SCREEN_HEIGHT / 2;
if (draw_start < 0)
    draw_start = 0;

draw_end = line_height / 2 + SCREEN_HEIGHT / 2;
if (draw_end >= SCREEN_HEIGHT)
    draw_end = SCREEN_HEIGHT - 1;
  • If perp_wall_dist = 1.0: line_height = 600 (occupies full screen).
  • If perp_wall_dist = 2.0: line_height = 300 (half screen).
  • If perp_wall_dist = 0.5: line_height = 1200 (clamped to viewport boundaries).
🖼️ The 3 Screen Zones

For every pixel $(x, y)$ in vertical column $x$:

Zone 1: Ceiling ($0 \le y < \text{draw\_start}$)
Filled with ceiling_colour
Zone 2: Wall Slice ($\text{draw\_start} \le y \le \text{draw\_end}$)
Sampled from the corresponding wall texture
Zone 3: Floor ($\text{draw\_end} < y < \text{SCREEN\_HEIGHT}$)
Filled with floor_colour

Part 10: Graphics Engine

Rendering with MiniLibX: Double Buffering

Why directly calling mlx_pixel_put creates tearing and how image buffers fix it

🐌 The Naive Mistake

Calling mlx_pixel_put(mlx, win, x, y, color) pixel by pixel:

  • Sends an X11 / Cocoa IPC packet for every single pixel!
  • For an $800 \times 600$ window: $480,000$ system calls per frame!
  • FPS drops to ~2 frames per second, screen flickers violently.
⚡ The Professional Solution: Image Buffer

We allocate one contiguous screen memory buffer:

game->img = mlx_new_image(game->mlx, 800, 600);
game->addr = mlx_get_data_addr(game->img, &bpp, &line_len, &endian);
🚀 Direct Memory Writing

Our custom pixel put function writes directly to RAM:

void my_mlx_pixel_put(t_game *game, int x, int y, int color)
{
    char *dst;

    if (x < 0 || x >= SCREEN_WIDTH || y < 0 || y >= SCREEN_HEIGHT)
        return ;
    dst = game->addr + (y * game->line_len + x * (game->bpp / 8));
    *(unsigned int *)dst = color;
}
  • O(1) memory write. Instant execution!
  • Once the entire frame is drawn in memory, we call mlx_put_image_to_window() once. Zero flicker, locked 60+ FPS!
Part 11: Movement & Controls

Movement, Rotation & Wall Sliding

Smooth navigation without getting stuck on walls

🎮 Movement & Wall Sliding

When pressing W/S (forward/back) or A/D (strafe):

  • We check the X coordinate and Y coordinate independently.
  • If the player walks diagonally into a vertical wall, X movement is blocked, but Y movement still succeeds!
  • Result: The player smoothly slides along the wall instead of coming to an abrupt halt!
// Independent axis check with buffer:
buf = 0.1;
if (map[(int)pos_y][(int)(new_x + buf)] != '1')
    player.pos_x = new_x;
if (map[(int)(new_y + buf)][(int)pos_x] != '1')
    player.pos_y = new_y;
🔄 Camera Rotation Matrix

When turning left or right with arrow keys, we rotate both the Direction vector and the Camera plane vector using the 2D rotation matrix:

// [ cos(θ)  -sin(θ) ] * [ x ]
// [ sin(θ)   cos(θ) ]   [ y ]

old_dir_x = dir_x;
dir_x = dir_x * cos(rot) - dir_y * sin(rot);
dir_y = old_dir_x * sin(rot) + dir_y * cos(rot);

old_plane_x = plane_x;
plane_x = plane_x * cos(rot) - plane_y * sin(rot);
plane_y = old_plane_x * sin(rot) + plane_y * cos(rot);
  • Keeping both vectors in sync ensures the FOV never distorts while turning.

Part 13: Memory Safety

Memory Lifecycle & Zero-Leak Architecture

Guaranteed clean exits across all termination triggers

🧹 Complete Cleanup in close_game()
int close_game(t_game *game)
{
    if (!game)
        exit(0);
    // 1. Free 2D map string array
    if (game->map)
        free_2d_array(game->map);
    // 2. Free 4 texture paths and XPM images
    free_textures(game);
    // 3. Destroy screen frame buffer
    if (game->img)
        mlx_destroy_image(game->mlx, game->img);
    // 4. Destroy window & display connection
    if (game->win)
        mlx_destroy_window(game->mlx, game->win);
    destroy_mlx(game);
    exit(0);
}

Part 14: Peer Defense Guide

Top Peer Evaluation Questions & Answers

Quick reference for the questions evaluators ask most often

Q1: What is DDA and why did you choose it over stepping by 0.01?
A: DDA stands for Digital Differential Analysis. Stepping by a fixed float (like 0.01) is slow and can miss wall corners. DDA calculates the exact mathematical distance to the next grid line ($X$ or $Y$), jumping directly from boundary to boundary. It guarantees 100% precision with the minimal number of loop cycles.
Q2: Why do you calculate perpendicular distance instead of normal Euclidean distance?
A: Normal Euclidean distance measures the hypotenuse from the player to the hit point. Since diagonal rays travel farther to reach the same flat wall than rays facing straight ahead, drawing lines based on Euclidean distance bends flat walls into spherical fishbowls (the fisheye effect). Perpendicular distance projects the distance onto the viewing direction vector, keeping walls flat.
Q3: How does your flood fill check that maps are enclosed without crashing on big maps?
A: Recursive flood fill creates a new stack frame for every cell, causing a stack overflow on large maps. We implemented an iterative Breadth-First Search (BFS) using a heap-allocated queue. It first marks true external spaces from the borders, then verifies the player area never touches open boundaries or internal holes.
Q4: How do you prevent memory leaks when pressing ESC or when the map is invalid?
A: Both the window 'X' event and KEY_ESC are unified into close_game(), which destroys all MLX images, windows, displays, texture paths, and 2D map arrays. In the parsing routines, all temporary ft_split buffers are freed before calling error_exit().
